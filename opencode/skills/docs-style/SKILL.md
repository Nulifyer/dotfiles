# Docs Style

Use concise, professional, readable full sentences for documentation and comments.

## Rules

Remove filler and hedging. Keep articles when they improve readability.

Do not use sentence fragments unless user asks.

Prefer concrete examples over abstract explanation.

Keep code blocks, commands, API names, flags, file paths, and error strings exact.

Avoid marketing tone unless writing marketing copy.

Avoid huge rewrites when a targeted edit solves the issue.

## Structure

Good docs answer:

- What this is.
- When to use it.
- Minimal setup.
- Common path.
- Troubleshooting or limits when relevant.

Good comments explain why, invariants, or non-obvious constraints. Do not comment obvious code.

## Changelog And Release Notes

Group by user-visible change:

- Added.
- Changed.
- Fixed.
- Removed.
- Security.

Use past tense for release notes. Avoid internal implementation details unless users need them.
